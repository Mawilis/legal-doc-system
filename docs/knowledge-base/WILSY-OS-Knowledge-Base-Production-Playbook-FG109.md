## 1. KNOWLEDGE BASE PURPOSE

Wilsy OS Knowledge Base is the production memory layer for the platform. It turns completed component work, stable releases, evidence routes, operating rules, and user workflows into searchable, printable, permissioned knowledge.

The Knowledge Base must not become a loose folder of PDFs. Each important update must ship with a manifest entry, source markdown, machine-readable JSON, saved PDF, proof sidecar, searchable metadata, and a release guard path.

- Users get plain-language operating guidance.
- Investors get evidence that the product can explain, prove, and govern itself.
- Engineers get release contracts that prevent future regressions.
- Auditors get proof that the PDF, JSON, source posture, owner, and hashes align.

---

## 2. EXECUTIVE SUMMARY

The Knowledge Base is now ready to behave like a production operating surface: it has a consolidated operating bar, live search, manifest-backed saved artifacts, proof records, permission-aware Vault routes, and controlled document actions.

FG109 adds the missing production ritual. Every completed component or UI surface should now produce a user guide, investor guide, engineering guide, JSON companion, PDF export, and proof sidecar before the work is treated as release complete.

- Production posture: saved artifact access, proof sidecar verification, and permissioned routes.
- Commercial posture: each feature can be explained to buyers, operators, and investors from the product itself.
- Engineering posture: every future component receives a documented operating contract and test/guard checklist.

## 3. USER OPERATING GUIDE

Users should open the Knowledge Base when they need a trusted answer about how a Wilsy OS surface works. The Vault should answer from saved artifacts only, then let the user open the PDF, inspect evidence, download, print, copy fingerprints, or open the companion JSON.

- Search by title, feature, audience, owner, proof posture, release label, category, or fingerprint.
- Use Open to preview the saved PDF inside the workspace.
- Use JSON to inspect the machine-readable playbook for training, automation, and AI retrieval.
- Use Evidence to inspect the proof sidecar and hash alignment.
- Use Copy fingerprint when a customer, auditor, or support case needs immutable proof.

## 4. INVESTOR READINESS GUIDE

The investor story is not that Wilsy OS has documentation. The investor story is that Wilsy OS turns product execution into governed institutional memory. A feature does not disappear into code; it becomes an artifact with purpose, proof, user training, and engineering continuity.

This creates a scalable diligence surface. Investors can inspect whether the platform knows what was shipped, why it matters, how it is used, how it is controlled, and what evidence proves it.

- Every strategic component can become a diligence-ready Knowledge Base asset.
- The PDF is the boardroom-readable artifact.
- The JSON is the machine-readable artifact for search, AI retrieval, and future automation.
- The proof sidecar binds the PDF to SHA3, owner identity, source posture, required text, and forbidden text.
- The manifest makes the document discoverable in the authenticated Vault.

---

## 5. ENGINEERING RELEASE GUIDE

When a component or UI surface is created or materially updated, the release is not complete until the Knowledge Base artifact is created or updated. This makes production knowledge part of the engineering definition of done.

- Inspect JSX ownership, backend routes, guards, state, effects, and evidence contracts before writing docs.
- Create or update the markdown playbook in docs/knowledge-base.
- Create or update the JSON companion with sections, audiences, routes, source files, release checklist, and evidence sources.
- Generate or refresh the PDF through the approved artifact workflow.
- Generate or refresh the proof sidecar with PDF SHA3 and canonical section declarations.
- Add or update the manifest entry with pdfPath, jsonPath, proofPath, audiences, permissionScope, search terms, requiredPdfText, and forbiddenPdfText.
- Run documentation guard, secret guard, Knowledge Base guard, and the client build when the surface touches frontend code.

## 6. RUNTIME CONTRACT

The Knowledge Base runtime contract is source discipline. The Vault reads saved artifacts from the manifest. It should not regenerate documents just because a user wants to read, print, download, or inspect evidence.

- Manifest source: client/src/data/wilsyKnowledgeBaseManifest.js
- Vault list route: /api/knowledge-base/vault
- Saved PDF route: /api/knowledge-base/vault/:id/pdf
- Saved JSON route: /api/knowledge-base/vault/:id/json
- Proof route: /api/knowledge-base/vault/:id/proof
- Generation route: /api/generate/pdf
- Forbidden legacy route: /api/crm/leads/views/proof-pack/export/pdf

## 7. PDF AND EVIDENCE ROUTE CONTRACT

The PDF and JSON artifacts are saved Knowledge Base assets. The proof sidecar is the verification record. These three files serve different jobs and should not be collapsed into one generic blob.

- PDF: human-readable guide for users, investors, operators, and auditors.
- JSON: structured guide for Knowledge Base search, AI retrieval, training flows, and automation.
- Proof JSON: hash-bound verification record for release integrity.
- All saved artifact routes must preserve authentication, institutional request headers, and no-regeneration discipline.
