# Part II: Institutional Engineering Laws

### LAW EK-001: Repository Evidence First

#### Purpose
The Engineering Kernel recognizes repository evidence as the highest authority for engineering decisions. Repository evidence ensures that engineering work is verifiable, reproducible, and independent of assumptions or undocumented claims.

#### Constitutional Rule
No engineering claim possesses institutional authority until it is supported by verifiable repository evidence.

#### Engineering Rationale
Repository evidence protects Wilsy OS from architectural drift, undocumented changes, duplicated implementations, and unverifiable engineering decisions. Evidence creates a permanent institutional record that future engineers and automation systems can trust.

#### Repository Evidence Requirements
Every engineering claim shall be supported by one or more of the following:
* Repository file inspection
* Git history / Git diff
* Repository tree maps
* File metadata metrics
* Build and compiler output
* Guard verification logs
* Unit and integration test results
* Runtime verification telemetry
* Measured execution evidence

Claims of completion, implementation plans, AI reasoning, generated responses, task status messages, or undocumented observations shall never be accepted as repository evidence. Only independently verifiable repository artifacts possess institutional authority.

#### Engineering Obligations
Every engineer, automation workflow, AI system, and Engineering Kernel module shall obtain repository evidence before proposing, approving, or implementing repository mutations.

#### Violation
Engineering work performed without repository evidence shall be considered unverified and shall not be accepted as institutional knowledge.

#### Compliance Requirements
Every Engineering Packet shall include a Repository Evidence section before any implementation or approval activity.

#### Constitutional Rule

#### Compliance Requirements

* Raw evidence without cryptographic digest binding shall be rejected as untrusted state.

### ENGINEERING KERNEL LAYERING RULE

#### Purpose
Define the mandatory dependency structure of the Engineering Kernel.

#### Rules
The Engineering Kernel shall be organized into architectural layers. The minimum approved layers are:
1. Domain
2. Application
3. Infrastructure
4. Interface

#### Responsibilities
* **Domain Layer**: Defines immutable institutional models and engineering contracts.
* **Application Layer**: Implements engineering behavior using Domain models.
* **Infrastructure Layer**: Provides repository access, filesystem interaction, serialization, and external integration.
* **Interface Layer**: Provides command line interfaces and future operator interfaces.

#### Dependency Rules
* The Domain layer shall not depend upon any other Engineering Kernel layer.
* The Application layer may depend only upon the Domain layer.
* The Infrastructure layer may depend upon the Domain layer.
* The Interface layer may depend upon the Application layer.
* Circular dependencies are prohibited.

#### Repository Evidence Requirement
* Repository structure maps.
* Import statements metrics.
* Python compilation verifications.
* Dependency inspection logs.

### ENGINEERING KERNEL ORCHESTRATION RULE

#### Purpose
Establish the Application Layer as the orchestration boundary of the Wilsy Engineering Kernel.

#### Rule
Application modules shall coordinate Engineering Kernel services.
* Application modules shall not implement parsing logic.
* Application modules shall not implement validation logic.
* Application modules shall not implement normalization logic.
* Application modules shall not implement serialization logic.
* Application modules shall not implement repository mutation logic.
* Application modules shall not implement institutional decision logic.

Application modules shall remain responsible only for coordinating immutable Engineering Kernel services and returning institutional models.

#### Engineering Rationale
Separating orchestration from implementation reduces coupling, preserves single responsibility, and allows Engineering Kernel capabilities to evolve independently without destabilizing application services.

#### Repository Evidence Requirement
* Repository structure maps.
* Dependency inspection logs.
* Python compilation verifications.
* Engineering packet validation output confirming implementation responsibilities reside within dedicated modules.

#### Violation Consequences
Embedding implementation logic inside application orchestration creates architectural coupling, duplicated responsibilities, reduced testability, increased blast radius, and institutional drift. Engineering packets violating this rule shall not be considered institutionally complete.
